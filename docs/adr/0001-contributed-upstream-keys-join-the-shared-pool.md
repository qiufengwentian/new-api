# 用户贡献的上游 Key 进入全站共享池

用户主动提交的第三方上游 Key，经探活通过后**追加**进管理端为该渠道类型指定的一条多密钥「承载渠道」，随该渠道为**全站**用户转发请求；贡献者以此换取回馈（见 ADR-0002）。贡献不新建渠道——承载渠道是管理端资产，其分组、优先级与模型白名单由管理端决定。这个决定难以反悔，而且外人会质疑为何拿陌生人的凭证服务他人请求，所以必须记录。

## Consequences

- 贡献者必须被明确告知、主动同意（提交页强制勾选），并且必须能自助撤回。没有这两条，本决定无法辩护。
- 探针返回 401 即判死：取消该贡献对应的订阅、从承载渠道移除该 Key、通知贡献者，且该 Key 的指纹**全局永久**不可再提交。上游偶发鉴权故障同样返回 401，所以「一把被误判的 Key 不可恢复」是这个规则的已知代价，已被接受。
- 多密钥渠道不参与渠道级余额查询（`controller/channel-billing.go:596-602`、`:629-631`），因此上游余额耗尽不会自动禁用承载渠道；余额不参与判死，订阅照常发放。
- 承载渠道的多把 Key 以「索引 → 状态」记在 `ChannelInfo.MultiKeyStatusList`，而删除一把 Key 会内联重排其余所有索引（`controller/channel.go:2030-2111`）。因此贡献记录**按 Key 指纹追踪，绝不按索引**。
- 「渠道不能没有 Key」是这个仓库的既有不变式：`delete_key` 拒绝删除最后一把 Key（`controller/channel.go:2082-2088`）。
